# 微信小游戏牌局流程对照

依据：`wxd0e404d795ea6f80_unpacked/game.js` 与 `src/GameBase/game.js`。

## 入场与下一局

- 首次快速匹配：`qAa(3, roomId, -1, -1, [])` → `15803 SitDown`。首次入场不是手动 Ready。
- 同桌再来一局：玩家仍在桌上且 `changeTable=false` 时调用 `ready(0, roomId, tableId, tlvs)` → `15810`。
- 换桌：`changeTable=true` 时再次调用 `qAa(3, roomId, -1, -1, tlvs)` → `15803`。
- 退出房间：`RequestStandUp` → `15804`，随后回到选场界面。
- QuickGame `isLocked=true`：登录房间后执行 JS `Qqa(InfoType=2)` → `15806`，展开
  `CResponseSvrInfoHGPara` 中的 TLV `10014` GameSo union，恢复断线牌局。
  当前小游戏的 `Pqa` 请求是 protobuf `08 02`，不是原生 TDR `00 02`。
- `Qqa` 的 `08 02` 必须同时使用 CCS `protocolVersion=23` 和内层 `sequence=0`；把 PB
  消息装进 `protocolVersion=0` 的 TDR 帧时，GameSvr 只继续响应 `15812` 心跳而丢弃 `15806`。
- 当前服务器的 `15806` 具有非对称编码：请求是 PB，响应仍是 `Xja` 原生 TDR
  (`u32 ResultID + u16 InfoType + u16 TLVNum + TTLVUNIT[]`)。响应解码先严格校验 TDR，
  仅在布局不匹配时回退 descriptor protobuf。
- `nf` 的字段顺序是消息号、类型、序号、源实体、目标实体、源 ID、目标 ID。`Qqa` 在发送
  `15806` 前把 `KBa`（目标实体）设为 `0`，其余路由 ID 也保持 `0`；登录、坐下、准备、
  GameSo 和心跳使用同一直接 GameSvr 头。通用 Lotus 头（目标实体 `1`、ID `-1`）会让
  当前 GameSvr 静默丢弃 `15806`，表现为只有心跳返回而请求最终 `TimeoutException`。
- `15809` 的 `type=6` 是“某一名玩家已准备”。只有事件 `PlayerID/SeatID` 指向本机时才把
  本机阶段切到 `READY`；对手先准备时仍须保留本机 `READY/CHANGE_TABLE/LEAVE_ROOM` 操作。

## 出站操作

`g.vK → g.nra` 统一使用 `15813 / CRequestPlayHGPara`：

- 叫/抢：`Pm/uJa subtype=6`，`zKa.Xyd=0/1`。
- 普通加倍：`subtype=11, Yg=2, mHc=1`。
- 默认模式不加倍：`subtype=11, Yg=1, mHc=1`。
- 超级加倍：`subtype=11, Yg=4, mHc=2`。
- 出牌/不出：`subtype=4`，使用 `sKa.{Zb,bd,yf,BT}`。

手牌按斗地主点数 `3…K、A、2、小王、大王` 排序，同点数按原始牌编码稳定排序。
玩家“不出”时保留上一手有效牌；两家连续不出、操作权回到上一手玩家时才清空压制目标。
出牌前先校验牌型、张数和主点是否能压过上一手，再提交给 GameSvr。

`15809` 的玩家详情 TLV `10001` 会解析 UIN、昵称、状态、桌号和座位。桌面保留最近
50 条结构化操作记录，包括准备、叫/抢地主、地主结果、底牌、加倍、托管、出牌/不出和结算。
玩家详情继续解析头像 URL，头像、昵称、UIN、座位、准备状态和剩余牌数直接显示在桌面。
房间事件 1..17 均进入操作记录，其中进入/退出、坐下/离桌、开始、准备、旁观、余额、
道具和牌桌结束使用明确名称，其余事件保留原始事件号。

托管状态按服务器 `wk` 位掩码维护（客户端托管位 1、服务器托管位 4）。托管期间始终显示
“取消托管”，不会再被后续出牌轮转覆盖。玩家自己选择“不出”时提示和记录均标记为“我”。

本机座位只能由登录/坐下结果、本机 15809 事件或发牌/同步手牌通知更新；其他玩家的 15809 SeatID 不得覆盖本机座位。
